FDR Portal: Phase-by-Phase Build Guide




  FDR Portal: Phase-by-Phase Build Guide
  This guide explains how to build each part of the Security Deposit / FDR Management
  Portal, in order. For every phase it gives the design decisions, schemas, endpoints, logic,
  screens and checks. It deliberately leaves out scheduling, team split and presentation
  material. Use it alongside the Build Roadmap, which holds the scope tiers (Must, Should,
  Could).


  Conventions used throughout
        Stack assumed: React + TypeScript (Vite), Node + TypeScript (Express), PostgreSQL
        16, Docker Compose. Everything translates directly to FastAPI or NestJS.
        Dates and money: deadline dates (issue, maturity, due) are DATE , never timestamps.
        Event times are TIMESTAMPTZ . Money is NUMERIC(14,2) , never floats. Compute the
        business date in Asia/Kolkata.
        One clock: no business logic calls new Date() or NOW() . Everything reads the app
        clock built in Phase 1.
        Transactions: every state change runs inside a database transaction that also writes
        an audit event.
        API: prefix /api/v1 , JSON, errors shaped as { code, message, details } . IDs are
        UUIDs.
        Layering: routes call services, services call repositories. Business rules live only in
        services.
        Verification versus lifecycle: the lifecycle status says where an instrument is in its life.
        A separate verification_state says how much of it is proven. The Roadmap listed
        Verified as a lifecycle step; here it is tracked by verification_state , and ACTIVE
        means an officer has accepted the instrument.

  1.4 State machine
  Keep the allowed transitions in one table and enforce them in one function.

     const ALLOWED: Record<Status, Status[]> = {
       DRAFT: ['SUBMITTED'],
          SUBMITTED: ['UNDER_SCRUTINY', 'RETURNED'],
          UNDER_SCRUTINY: ['ACTIVE', 'RETURNED'],
          RETURNED: ['SUBMITTED'],
          ACTIVE: ['EXPIRING', 'RELEASE_REQUESTED'],
          EXPIRING: ['MATURED', 'RENEWED', 'RELEASE_REQUESTED'],
          MATURED: ['RENEWED', 'LAPSED', 'RELEASE_REQUESTED'],
          LAPSED: ['RENEWED', 'RELEASE_REQUESTED'],
          RELEASE_REQUESTED: ['RELEASED', 'ACTIVE', 'EXPIRING', 'MATURED', 'LAPSED'],
          RENEWED: [],
          RELEASED: [],
     };


     export async function transition(tx, inst, to: Status, actor, extra?) {
       if (!ALLOWED[inst.status].includes(to)) throw new
     InvalidTransition(inst.status, to);
       const before = { status: inst.status };
       await tx.none('UPDATE instruments SET status = $1, updated_at = now() WHERE
     id = $2', [to, inst.id]);
       await recordEvent(tx, { actor, action: 'STATUS_' + to, entityType:
     'instrument', entityId: inst.id, before, after: { status: to, ...extra } });
     }


   RELEASE_REQUESTED can return to the earlier status if the request is rejected. Store that
  earlier status in status_before_release when entering RELEASE_REQUESTED , and
  restore it on rejection.

  Never update status anywhere except through transition .

  2.3 Validation
  Use the same zod schema on the client and server (share it from a shared/ package or
  duplicate it carefully).

         reference_no : 6 to 30 characters, letters, digits and hyphens.

         issuing_bank : chosen from a list (the same list the mock bank knows).

         amount : greater than 0 and below a sanity ceiling (for example 100 crore), two
        decimals.
         issue_date : not after today() .

         maturity_date : after issue_date , and not before today() at submission.

         beneficiary_name : required, trimmed, internal spaces collapsed.
         type : one of the enum values.

  Business rules run in the service at submit time and return 422 with details listing
  every failing field, so the form can show all errors at once.


  2.4 Document upload
        Use multer with disk storage, a 10 MB limit and a single-file field.
        Allow PDF, PNG and JPEG only. Check the real type from the file's first bytes (for
        example with the file-type package), not from the extension or the browser's mime
        header.
        Compute SHA-256 while saving.
        Store at STORAGE_DIR/<instrumentId>/<uuid>.<ext> . Never build the path from the
        original filename. Keep the original name only in the database, sanitised for display.
        If the same checksum already exists on the same instrument, accept it but return a
         duplicateOf hint so the UI can warn.
        Download endpoint: check authorisation first, then stream the file with Content-
        Disposition: attachment , and write a DOCUMENT_ACCESSED event. Files are never
        served by a public static route.

  2.5 Submit logic
   1. Load the instrument in a transaction with FOR UPDATE .
   2. Check ownership, then that status is DRAFT or RETURNED .
   3. Run field validation and compute missing documents from the required_docs rule. If
        anything is missing, return 422 listing exactly what.
   4. Upsert one field_provenance row for each of: reference_no , issuing_bank ,
         amount , issue_date , maturity_date , beneficiary_name , with tier CLAIMED and
        source institution .
   5. Set submitted_at from the app clock and verification_state = 'UNVERIFIED' .
   6. Call transition(... 'SUBMITTED') . This writes the audit event.

  A second submit on an already submitted instrument fails with an invalid-transition error,
  which makes the endpoint safe against double clicks.


  2.6 Editing rules
        Only the owning institution may edit, and only in DRAFT or RETURNED .
        Every edit records before and after values as an event.
        On resubmission after a return, any field whose value changed goes back to tier
        CLAIMED , and verification_state returns to UNVERIFIED . This rule matters:
        changing a value must never keep a confirmation that belonged to the old value.


  2.7 Frontend
        A three-step form: Details, Documents, Review and submit. Save as draft at every
        step.
        Show server errors next to the exact fields using details .
        Document panel: pick the document type, upload, list with size and checksum prefix,
        remove button while editable.
        Institution home: a table of instruments with a status chip, maturity date, days
        remaining (computed on the server from the app clock) and a clear call to action when
        an instrument is RETURNED .


  2.8 Edge cases to handle

  3.1 The mock bank service
  A separate Node process with its own data, exposing:

         POST /verify with { reference_no, bank, amount, issue_date, maturity_date,
        beneficiary_name } .

         GET /records and POST /reload (development only, for showing and resetting the
        bank's data).
         GET /health .

  Its data is a JSON file of bank records { bank, reference_no, amount, issue_date,
  maturity_date, beneficiary_name, status } produced by the seed script. Behaviour:

   1. If the bank is in a configured offline list, return HTTP 503 with { result:
        'UNAVAILABLE' } .
   2. Look up (bank, reference_no) . If absent, return { result: 'NOT_FOUND' } .
   3. If the bank is in the configured slow list, the first call for a given reference returns {
      result: 'PENDING', retry_after_seconds: 10 } and remembers the time. Calls
        after that interval return the real result.
   4. Otherwise compare each submitted field with the record and return:

          'result': 'MISMATCH',
          'bank': 'Example Bank',

  3.3 Verification service
  Call the bank outside any database transaction, so a slow network never holds locks.

       const res = await callBank(payload, { timeoutMs: 5000 });                // network, no

          await withTransaction(async tx => {

   applyResult by outcome:

         CONFIRMED: set tier BANK_CONFIRMED (source bank:<response_id> ) on all six fields;
         verification_state = 'CONFIRMED' ; auto-resolve any open discrepancies with the
         note Confirmed by bank response <id> .
         MISMATCH: for each field with match = false , insert an OPEN discrepancy (skip if
         one is already open), leaving that field at its current tier. Fields that match become
         BANK_CONFIRMED . verification_state = 'MISMATCH' .
         NOT_FOUND: treat as a mismatch on reference_no with the confirmed value empty
         and the reason No record at bank .

        PENDING: verification_state = 'PENDING' . The officer re-requests later (see the
        retry hint).
        UNAVAILABLE or timeout: verification_state = 'UNAVAILABLE' . The case needs

  Every outcome writes an event ( VERIFICATION_REQUESTED , VERIFICATION_RESULT ) and

  3.4 Comparison and normalisation
  Normalise both sides before comparing, so cosmetic differences do not create false
  discrepancies.

        Amounts: parse to two decimals, compare as strings of that form.
        Dates: ISO YYYY-MM-DD .
        Names: uppercase, trim, collapse spaces, remove dots and commas.
        Reference numbers: uppercase, strip spaces.

  Do the comparison in the mock bank (it decides match ) and again defensively in the main
  app when building the discrepancy card values.


  3.5 Trust tier rules
        CLAIMED: only the institution provided the value.
        DOCUMENT: an officer confirmed the value against an attached document. Endpoint
        POST /instruments/:id/fields/:field/check-document {documentId} . It may raise
         CLAIMED to DOCUMENT , and never lowers BANK_CONFIRMED .
        BANK_CONFIRMED: a bank response matched the value.
        Editing a field (Phase 2 rule) always resets it to CLAIMED .
        The tier shown for the instrument header is the lowest tier among the six fields,
        because an instrument is only as proven as its weakest field.

  3.7 Queue query

     SELECT i.id, i.reference_no, i.issuing_bank, i.amount, i.maturity_date,
            i.verification_state, i.status, inst.name AS institution, inst.region,
                   (SELECT count(*) FROM discrepancies d WHERE d.instrument_id = i.id AND
     d.status = 'OPEN') AS open_discrepancies,
            i.submitted_at
     FROM instruments i JOIN institutions inst ON inst.id = i.institution_id
     WHERE i.status IN ('SUBMITTED','UNDER_SCRUTINY')
         AND ($1::text IS NULL OR inst.region = $1)
         AND ($2::text IS NULL OR i.issuing_bank = $2)
         AND ($3::text IS NULL OR i.verification_state = $3)
     ORDER BY i.submitted_at ASC
     LIMIT $4 OFFSET $5;

  3.10 Checks
        A clean instrument turns every field bank-confirmed and shows CONFIRMED .
        A tampered amount produces exactly one open discrepancy for amount , and the card
        shows both values.
        An offline bank yields UNAVAILABLE without breaking the page.
        A slow bank returns PENDING , then a real result on retry after the interval.
        Accept is refused while a discrepancy is open, and allowed after resolution with a note.

  4.3 The evaluation job
   evaluate(asOf) runs in one transaction, guarded by an advisory lock so two runs cannot
  overlap ( SELECT pg_advisory_xact_lock(42) ). It returns a summary object. Run its
  steps in this order.

  Step 1: status sweeps, applied one after another so a large clock jump cascades
  correctly

   1. ACTIVE to EXPIRING when maturity_date - asOf <= the largest reminder
     offset (90 days by default).
   2. EXPIRING to MATURED when maturity_date <= asOf .
   3. MATURED to LAPSED when asOf > maturity_date + graceDays and no renewal
        instrument exists for it.

  Each change goes through transition() with the actor system . Instruments in DRAFT ,
  SUBMITTED , UNDER_SCRUTINY , RETURNED , RENEWED , RELEASE_REQUESTED and RELEASED
  are not swept.

  Step 2: maturity reminders



                                                                                       Page 19 of 29
FDR Portal: Phase-by-Phase Build Guide




  For each live instrument compute daysLeft . Find the tightest offset already crossed
  ( daysLeft <= offset ). Create one alert for that offset per recipient role. Insert every
  looser offset as an already-resolved alert with resolution = 'SUPERSEDED' , so a jump
  from day 100 to day 10 produces one alert, not four.

  Step 3: process alerts

         Pending verification: instruments in SUBMITTED or UNDER_SCRUTINY with
         verification_state in ( UNVERIFIED , PENDING , UNAVAILABLE ) older than
         afterDays .
         Open discrepancy: any OPEN discrepancy older than afterDays .
         Overdue renewal: MATURED or LAPSED instruments with no successor.
         Release pending: release requests waiting longer than afterDays .

  Step 4: escalation

  For each OPEN or ACKNOWLEDGED alert, compute its age in days since creation. If the age
  reaches the next level's afterDays , insert the next-level alert (new dedupe_key because
  level is part of it), set the old alert to ESCALATED , and write an event.

  Step 5: auto-resolution

  Each alert kind has a function stillRelevant(alert, state) . Close alerts whose
  condition no longer holds (verification confirmed, discrepancy resolved, renewal
  accepted, instrument released) with resolution = 'SYSTEM_CONDITION_CLEARED' .

     async function evaluate(tx, asOf: string) {
          await tx.none('SELECT pg_advisory_xact_lock(42)');
          const rules = await loadRules(tx);
          const s = { statusChanges: 0, alertsCreated: 0, escalations: 0, resolved: 0
     };
          s.statusChanges += await sweepStatuses(tx, asOf, rules);
          s.alertsCreated += await maturityReminders(tx, asOf, rules);
          s.alertsCreated += await processAlerts(tx, asOf, rules);
          s.escalations   += await escalate(tx, asOf, rules);
          s.resolved                     += await autoResolve(tx, asOf);
          return s;
     }


  Every insert uses ON CONFLICT (dedupe_key) DO NOTHING , so a second run on the same
  date changes nothing and returns zeros.

  5.4 Activating the chain
  Inside the accept service (Phase 3), after the replacement moves to ACTIVE :

   1. If parent_instrument_id is set, call transition(parent, 'RENEWED') with the actor
         and extra = { renewedBy: child.id } .
   2. Write RENEWED_BY on the parent and RENEWS on the child.

  5.5 Chain query

     WITH RECURSIVE up AS (
         SELECT * FROM instruments WHERE id = $1
         UNION ALL
       SELECT p.* FROM instruments p JOIN up ON up.parent_instrument_id = p.id
     ), down AS (
         SELECT * FROM instruments WHERE parent_instrument_id = $1
         UNION ALL
         SELECT c.* FROM instruments c JOIN down ON c.parent_instrument_id = down.id
     )
     SELECT * FROM up UNION SELECT * FROM down ORDER BY issue_date;

  6.2 Conditions
  Define them in a release_conditions rule so they are configurable. Defaults:


     Code                                Type     Meaning

      NO_OPEN_DISCREPANCY                auto     No open discrepancy on the instrument

      NO_BLOCKING_OBSERVATION            auto     No unresolved observation of severity
                                                  BLOCKING

      INSTRUMENT_VERIFIED                auto     verification_state is CONFIRMED , or an
                                                  override acceptance is on record

      REQUEST_DOCUMENTS_ATTACHED         auto     At least one release document is attached

      COMPLIANCE_CONFIRMED               manual   The requirement the deposit secured is
                                                  confirmed as fulfilled

      LIEN_REMOVAL_DOCUMENT              manual   Bank letter or request for lien removal is on file


  Auto conditions are evaluated live every time they are read, never stored as met. This is
  what lets the system block a decision when something changes after a recommendation.
  Manual conditions are ticked by an officer with remarks and stored. When a request is
  created, copy the configured conditions into release_conditions .


  6.3 Flow
   1. Request. POST /instruments/:id/release-requests {reason} (institution). Allowed
        when the instrument is ACTIVE , EXPIRING , MATURED or LAPSED with no open request.
        Store the current status in status_before_release , transition to
         RELEASE_REQUESTED , create the request in PENDING_CONDITIONS and copy the
        conditions. Release documents are uploaded with release_request_id set.
   2. Conditions. PATCH /release-conditions/:id {met, remarks} (officer) for manual
        items. GET /release-requests/:id returns every condition with its live state and, for
        failing auto conditions, a reason and a pointer to the cause.




                                                                                                Page 27 of 29
FDR Portal: Phase-by-Phase Build Guide




   3. Recommend. POST /release-requests/:id/recommend {remarks} (officer). Refused
        with 409 and the reasons unless every mandatory condition is met. Records a
         RECOMMEND row at level 1 and moves the request to PENDING_APPROVAL .
   4. Decide. POST /release-requests/:id/decide {decision, remarks} (approver).
        Remarks are mandatory for every decision.
             Recompute all auto conditions first. If any mandatory condition fails, return 409
             with reasons. This is the block.
             APPROVE: transition(instrument, 'RELEASED') , set closed_at , store
              refund_reference if given, and write an event whose after_json is a snapshot of
             every condition and its state at decision time.
             REJECT: restore status_before_release , set the request REJECTED .
             RETURN: set the request RETURNED . The institution can add information and
             resubmit, which sets it back to PENDING_CONDITIONS . The instrument stays
              RELEASE_REQUESTED .


  6.4 Controls
        Separation of duties: the approver must not be the same user who recommended.
        Concurrency: lock the request and instrument rows with FOR UPDATE in every step so
        two decisions cannot race.
        Configurable levels: a rule such as { levels: [{ level: 1, role: 'officer',
        action: 'RECOMMEND' }, { level: 2, role: 'approver', action: 'DECIDE' }],
        extraApprovalAbove: 5000000 } adds a further approver for large amounts.
        Implement the second level generally (a loop over configured levels) rather than
        special-casing it.
        Human decision: nothing in the system approves a release automatically. The screen
        says so.


  6.5 Interaction with other phases
        Maturity reminders for an instrument in RELEASE_REQUESTED stay visible, but the
        evaluation job adds a RELEASE_PENDING alert when the request waits too long.
        On RELEASED , auto-resolution closes every open alert on the instrument.
        A RENEWED instrument cannot be released (terminal). Only the live successor can.
